# tcp-kai — запросы к микросервисам по коллекциям tcp-kai

`tcp-kai` — CLI десктопного клиента tcp-kai. База общая с GUI:

- **коллекция = микросервис** (`coordinator`, `whois`, `fuzzing`, …),
- **запрос** = сохранённый NestJS-паттерн (`cmd`) с телом,
- **пак переменных = стенд** (`local`, `prod`, `server`) — в нём `host`/`port`
  для подстановки `{{host}}:{{port}}`.

Отправка из CLI попадает в ту же историю и так же поднимает запрос в сайдбаре
приложения, что и клик в GUI.

Установка бинаря:

```bash
# из бандла приложения (обновляется вместе с ним):
./scripts/install-cli.sh
# или из исходников:
cd src-tauri && cargo build --release --features cli --bin tcp-kai-cli
```

## Быстрый старт

```bash
tcp-kai ls                                  # какие микросервисы заведены (+ применённый пак)
tcp-kai ls coordinator                      # запросы сервиса (имя и cmd, если отличается)
tcp-kai envs coordinator                    # паки переменных и что в них лежит
tcp-kai history coordinator auth-login      # последние обмены (--full — с телами, --json)

tcp-kai coordinator auth-login              # отправить (пак — применённый в GUI)
tcp-kai coordinator auth-login -e local     # тот же запрос на другой стенд
tcp-kai whois lookup --json | jq .response  # машинночитаемо: в stdout только ответ сервиса
tcp-kai coordinator sync --timeout 300      # долгий запрос (сек; 0 — ждать вечно, дефолт 60)
tcp-kai notifier user-created --emit        # @EventPattern: кадр без id, ответ не ждать
```

`ls`/`envs`/`history` принимают `--json`. Шелл-дополнения: `tcp-kai completions zsh`.

## Импорт контрактов

Коллекцию можно наполнить прямо из NestJS-контракта (as-const объект/enum с
именем `*Cmd*` или контроллер с `@MessagePattern`):

```bash
tcp-kai parse  ../whois/src/contracts/cmd.contract.ts      # что нашлось (без базы)
tcp-kai import whois ../whois/src/contracts/cmd.contract.ts --dry-run
tcp-kai import whois ../whois/src/contracts/cmd.contract.ts # создать новые запросы
```

- Берутся только контейнеры, похожие на cmd-реестр (`WhoisCmd`, `cmd.enum`);
  остальное (имена сервисов, zod-схемы) пропускается, `--all` снимает фильтр.
- `@deprecated`-паттерны по умолчанию пропускаются (`--with-deprecated`).
- Существующие запросы не трогаются; чьи cmd ушли из контракта — перечисляются,
  но не удаляются. В GUI то же самое: ⌘P → коллекция → «Импортировать контракт»
  или просто перетащить `.ts`-файл в окно.

- Первый аргумент, не являющийся подкомандой, читается как имя коллекции:
  `tcp-kai coordinator auth-login` = `tcp-kai send coordinator auth-login`.
- Запрос ищется по имени, затем по `cmd`; регистр не важен. При опечатке CLI
  сам покажет похожие имена.
- **`-e` не меняет состояние приложения** — это разовый выбор стенда для этого
  вызова; применённый в GUI пак остаётся прежним.

## Тело запроса

По умолчанию едет тело, сохранённое в приложении. Перекрыть — разово:

```bash
tcp-kai whois lookup -d '{"domain":"example.com"}'
echo '{"limit":10}' | tcp-kai whois lookup      # из трубы
tcp-kai whois lookup -f body.json               # из файла ('-' = stdin)
```

Сохранённое в базе тело при этом **не перезаписывается** — в отличие от GUI,
где редактор и есть источник правды.

## Переменные

Порядок источников, каждый следующий перекрывает предыдущий:

1. пак из базы (`-e <пак>`, иначе применённый в GUI),
2. `sec` — только с `--from-sec`,
3. `--var key=value` — разовое значение.

```bash
tcp-kai fuzzing scan --var port=18099          # тот же пак, другой порт
tcp-kai coordinator auth-login --url 10.0.0.5:18009   # мимо пака целиком
```

Неизвестное имя остаётся в тексте как `{{name}}` — опечатка видна, а не
превращается в пустую строку. Если после подстановки `{{...}}` осталась в
строке подключения, CLI не пойдёт в сеть, а скажет, чего не хватает.

## Секреты: --from-sec

Секреты не хранятся в базе приложения, а приезжают из `sec` (скилл `sec`).
Раскладка:

| tcp-kai | sec |
|---|---|
| коллекция `coordinator` | проект `tcp-kai-coordinator` |
| пак `local` / `prod` | инстанс `-e local` / `-e prod` |
| `{{token}}` | ключ `TOKEN` (регистр не важен) |

```bash
sec set tcp-kai-coordinator/TOKEN -e prod      # завести (значение — скрытым вводом)
tcp-kai coordinator auth-login --from-sec      # подставить
tcp-kai envs coordinator                       # подскажет имя sec-проекта
```

- Из sec тянутся **только те ключи, что упомянуты в запросе** как `{{name}}`;
  остальные не запрашиваются.
- Значения идут через stdout дочернего процесса, не через argv.
- Бинарь sec: `TCP_KAI_SEC_BIN`, иначе `sec` из PATH.

## Что попадает в базу приложения

- В историю пишется тело **с `{{vars}}`, до подстановки** — секрет из sec в
  базу не уезжает.
- **Ответ сервиса пишется в историю как есть.** Если сервис возвращает токен
  (например `auth-login`), он окажется в истории — ровно как и при работе через
  GUI. Не нужно — `--no-history`.
- **Ошибки тоже пишутся** (с v0.4: флаг ok, cmd, фактический адрес и имя пака
  на момент отправки), история обрезается до лимита из настроек GUI
  (`history_limit`, по умолчанию 200 записей на запрос).
- Сама база (`~/Library/Application Support/com.kaidstor.app/app.db`) не
  шифрована: тела запросов с паролями лежат в ней открытым текстом. Это повод
  переносить их в sec, а не хранить в паке.

## Отладка

```bash
tcp-kai coordinator auth-login --dry-run   # показать кадр, не подключаясь
tcp-kai coordinator auth-login -v          # трассировка кадра в stderr
```

`--dry-run` и `-v` печатают тело после подстановки — с `--from-sec` там будет
живой секрет, в чат такое не копировать.

## Правила

- **Читать — свободно**: `ls`, `envs`, `--dry-run` ничего не меняют.
- **Отправка меняет состояние сервиса.** `get-*`/`*-list`/`read-*` выполнять
  спокойно; всё, что похоже на запись (`create-*`, `update-*`, `delete-*`,
  `send-*`), — только с явного подтверждения пользователя, и по умолчанию на
  `-e local`, а не на `prod`.
- Стенд по умолчанию — тот, что применён в GUI, и это часто `prod`. Если
  сомневаешься, куда полетит запрос, сначала `tcp-kai envs <ms>`.
